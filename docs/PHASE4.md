# PHASE4：测试、故障注入与压测

## 这一阶段做什么

阶段一到三把系统做出来了。阶段四证明它真的能用，证明三件事：

1. 功能对不对：单元测试、集成测试、题目 6.3 的 10 个 E2E 场景
2. 东西坏了扛不扛得住：题目 6.5 的故障注入
3. 人多了扛不扛得住：题目 6.4 的压测

对应评分"测试与压测 15%"，以及"高并发与架构 20%""可靠性与安全 15%"的证据。

完成标准：`make test` 和 `make loadtest` 可用；10 个 E2E 场景全部通过；`docs/FAULT_INJECTION.md` 和 `docs/LOADTEST.md` 完成。

## 关键设计决定（已定）

1. **测试分三层**，放在三个目录：
   - `tests/unit`：不启动任何服务，一个函数一个函数测
   - `tests/integration`：依赖 `make up` 启动的真实 PostgreSQL、Redis、RabbitMQ 和 mock 服务，测几个部件接在一起
   - `tests/e2e`：从 WebSocket 发消息进去，看最后的回复、数据库、审计，走完整链路
2. **`make test` 的定义**：前提是已经 `make up`。依次跑 unit（带覆盖率报告）、mock-llm 自身的测试、integration、e2e。任何一层失败，整体失败。
3. **测试代码不进生产镜像**：gateway、worker、scheduler、mock-* 的镜像里不能有 `tests/` 目录。tools 容器通过挂载或单独的构建目标拿到测试代码。具体用哪种方式 CC 选，汇报里说明理由。
4. **故障注入由 Jo 亲手做**。CC 只负责把 19 种故障都做成"一条命令注入、一条命令恢复"，并写好 `docs/FAULT_INJECTION.md` 的骨架。现象、排查过程、结论由 Jo 填，CC 不填。
5. **告警做最小版本**（题目 6.5 要求验证告警，这是新增的一小项）：熔断打开、消息进死信、Redis 连接失败时，打一条结构化日志，`level=error`，`event` 字段固定为 `alert`，带 `alert_type`、`trace_id`、`tenant_id`；同时对应的 `/metrics` 计数器加 1。不接真实告警通道，写进已知问题。
6. **压测用 k6**，放在 docker compose 里单独的 profile，不随 `make up` 启动。压测用户的 token 由脚本生成到一个不进 git 的文件里（加进 `.gitignore`）。
7. **mock-llm 速度调成接近真实大模型**：意图识别调用约 300 毫秒；流式生成首个字约 300 毫秒，之后每秒约 50 个字。这两个值可通过环境变量或 mockctl 改。压测报告用 meta 里的 `timings` 和 `llm_ms` 把 mock 耗时和系统自身耗时拆开写。
8. **压测结果如实写**。达不到题目指标时，写清楚当前硬件、瓶颈在哪、证据是什么、怎么改进，不为了凑数字调参数。
9. **时间不够时的保留顺序**：负面清单 > 10 个 E2E > 6.5 里标【必测】的故障 > 压测四个场景 > 覆盖率 > 其余。

## 步骤

### 4.1 丰富 mock 数据

**做什么**：
- mock-finance：u_a_1001、u_a_1004、u_b_1001 各有多笔订单，覆盖不同状态：发票已开具、发票未开具、退费审核中、已退款、余额有值和为 0。月份分散在最近三个月
- mock-platform：坐席在线和不在线可以用 mockctl 切换，排队人数可以设置
- tenants 表：t_a 每日 token 预算设为 2000000，t_b 设为 500000，写进种子数据
- `scripts/phase3_smoke.py` 的预算降级场景：测试前读出 t_b 原来的预算值，测试后恢复成这个原值

**为什么**：现在每个人只有一张订单，所有财务回复都一样，测不出"不同状态回复不同"。阶段五的评测集也要用这些数据。预算设上数字后，演示控制台的状态条能显示"用量 / 上限"，才能展示"成本控制与 token 预算"这个加分项。

**验证**：
- 用 `scripts/sql.py` 查三个用户的订单，贴出每人每笔的 order_id、状态、金额（只选这几列）
- 用 mockctl 把坐席切成不在线，发"转人工"，回复是留言方案；切回在线，回复是排队信息。贴两次回复原文
- 查 tenants 表 t_a、t_b 的 daily_token_budget
- 跑 phase3_smoke，贴最后几行，再查一次 t_b 的预算，仍是 500000

### 4.3 集成测试

**做什么**：在 `tests/integration` 下覆盖题目 6.2 点名的六项，每项至少一个测试：
- IM 入站：gateway 收到消息，回 ACK，RabbitMQ 里多一条
- 队列：worker 消费后 ACK；格式坏的消息进死信队列
- LLM mock：调用 mock-llm 拿到结构化的工具调用
- 知识检索：检索 SQL 带 tenant_id，t_a 查不到 t_b 的条款
- 财务 mock：带正确 token 能查，越权返回 403
- 提醒调度：插一条马上到期的提醒，scheduler 在 5 秒内推送并算出下一次时间

**为什么**：单元测试测不出"部件接在一起会不会出问题"，比如 SQL 真的跑在 pgvector 上、消息真的进了队列。

**验证**：贴 `pytest tests/integration -v` 的每个测试名和最后一行。

### 4.4 E2E：题目 6.3 的 10 个场景

**做什么**：`tests/e2e` 下每个场景一个测试，全部从 WebSocket 发消息进去，复用 phase2_smoke 和 phase3_smoke 的写法。每个测试检查三样：回复内容、数据库状态、审计或 meta。

1. 查询课程政策：回复带知识库出处
2. 查询发票：邮箱、手机号是打码的
3. 用户 A 查用户 B 财务：回复是拒绝话术，审计里有一条 forbidden；另外直接用 A 的 token 调 mock-finance 查 B，HTTP 403
4. 关闭自动续费：第一条回复要求确认，不执行；回复"确认关闭"后才调用 mock-platform，且只调用一次
5. "明天 9 点提醒"：用快进脚本，到点后 5 秒内收到推送
6. "转人工"：生成转接单，带摘要、意图、已尝试操作、风险标记
7. mock-finance 超时：回复不含任何金额数字，是"暂时查不到"话术，写了 followup_tasks
8. mock-llm 返回非法 JSON：回兜底话术，没有执行任何工具
9. 同一个 message_id 发两次：第二次回 duplicate，数据库里只有一条
10. 知识库无命中：回"我暂时没有查到明确依据，建议转人工确认"，没有调 LLM 生成

用到故障的场景（7、8），测试里用 mockctl 注入，结束时恢复。测试用句避开 mock-llm 已知的关键词碰撞（"你好，在吗""那寒假班呢"、注入句、转人工摘要）。

**为什么**：这 10 个是题目的验收标准。

**验证**：贴 `pytest tests/e2e -v` 的 10 个测试名和最后一行；再跑一次完整的 `make test`，贴最后一行。

### 4.6 压测

**做什么**：
- k6 脚本放在 `loadtest/`，`make loadtest` 跑下面四个场景（也能单独跑某一个）
- 生成压测用户：t_a 下至少 1500 个测试用户，token 写进不进 git 的文件
- mock-llm 速度按关键设计决定第 7 条设置
- 四个场景：
  1. 稳定：500 个 WebSocket 连接，每秒 200 条，持续 5 分钟
  2. 突发：至少 1000 个虚拟用户，每秒 1000 条，持续 30 秒。每个用户每 10 秒不超过 15 条，避开 10 秒 20 条的用户限流
  3. 财务查询：每秒 100 条财务问题
  4. LLM 超时率 20%：用 mockctl 设置，跑稳定场景的负载
- 采集：k6 自带的延迟和错误率；每 5 秒记一次 RabbitMQ 队列积压（管理接口）；每 5 秒记一次 `docker stats`
- 在消息里区分三个时间：ACK 耗时、首句耗时、完整回复耗时

**为什么**：题目 6.4 的四个场景。削峰靠队列，要看突发时队列积压多少、多久消化完。

**验证与报告**：写 `docs/LOADTEST.md`，每个场景包括：
- 本机硬件（CPU 核数、内存）、worker 副本数
- 实际 QPS；ACK、首句、完整回复三类耗时的 P50、P95、P99；错误率
- 队列积压最高值和消化完的时间
- 各容器 CPU、内存峰值
- 突发场景：发出的消息数和数据库里最终 replied 的消息数，两个数要相等，证明不丢消息
- 财务场景：完整回复的 P95，和 `timings.finance` 的 P95 分开写
- LLM 超时场景：系统没崩（服务都在、/health 正常），降级回复的比例，有没有触发熔断
- 耗时拆分：用 `llm_ms` 和 `timings` 拆出 mock-llm 耗时和系统自身耗时。说明阶段一"完整回复 3004ms"的原因
- 和题目指标逐条对比，没达到的写原因和改进方向
