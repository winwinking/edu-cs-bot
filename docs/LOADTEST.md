# 第二轮（长连接模型、预算已解除）—— 当前有效结果

## 环境与方法

- **硬件**：Docker Desktop 分给容器的资源是 16 CPU / 7.6GiB 内存（`docker info`），宿主机
  物理内存约 16GB。
- **worker 副本数**：场景 1 分别用 1 个和 3 个 worker 各跑一次完整规模做对比；场景 2/3/4
  （突发、财务查询、LLM 超时）统一用 3 个 worker 跑——原因见 AGENT_LOG"步骤 4.6 第二轮"里
  记录的决定：场景 1 的 1 worker 结果已经证明单 worker 吞吐量（约 10/s）远低于任何一个后续
  场景的目标速率，继续用 1 worker 跑只会重复同样的"排队等 CPU"结论、还要多花时间清理巨量
  积压，3 worker（约 37/s）虽然仍低于题目目标，但更能看清"扩容之后系统各环节（尤其是
  Postgres）的表现"，信息量更大。
- **t_a 机构每日 LLM token 预算**：Jo 手动执行 `UPDATE tenants SET daily_token_budget=NULL
  WHERE id='t_a'`，`.env` 里 `DEFAULT_DAILY_TOKEN_BUDGET` 本来就是空（不限额），两处确认过
  之后预算不再是限制因素，`meta.budget_exceeded` 在下面每个场景都用 SQL 核对过全程为
  `false`。
- **连接模型**：**从短连接改成长连接**（见 AGENT_LOG 索引第 34 条【人工审查发现】）。原来
  `loadtest/lib/ws_client.js` 每条消息各自 `ws.connect()` 一次、发完等完整回复就关闭连接，
  测的是"大量短连接各发一条消息"，不是题目"N 个连接持续发消息"这个模型。改成
  `runPersistentConnection()`：每个 VU 建一条连接、保持到场景结束，按固定间隔连续发消息，
  不等上一条回复回来就发下一条，用 `message_id`/`reply_to` 分别追踪每条在途消息。连接数和
  单连接发送速率配套计算（目标速率 ÷ 连接数），留出远低于网关限流（`RATE_LIMIT_USER_PER_10S
  =20`）的余量，具体数字见各场景小节。ACK/首句/完整回复三段耗时的起点统一改成"消息发出
  时"，建连耗时单独记 `ws_connect_latency_ms`，不再混进 ACK 耗时。发出数/ACK 数/回复数分开
  计数（`messages_sent`/`messages_acked`/`messages_replied`）。
- **先冒烟后满载**：四个场景的新脚本都先用 `-e` 环境变量跑了一次十几秒、个位数/十位数连接数
  的小规模冒烟，确认长连接模型、message_id 匹配、`ws_connect_latency_ms` 等新指标都符合预期
  之后才跑满载。
- **docker stats 采集方式**：跟第一轮一样，`collect_docker_stats.ps1` 是给人工开交互式窗口
  用的，本轮压测通过自动化工具后台调用，改用等价的 Bash 循环（每 5 秒 `docker stats
  --no-stream`）稳定采集，四个场景（含场景 1 的 1 worker 和 3 worker 两次）全部采集成功，
  没有再出现第一轮场景 1 第一次跑漏采的问题。
- **消息量级下压测机自身的资源**：k6 单容器本身 CPU/内存占用远小于 worker/rabbitmq，不是
  瓶颈。

## 每个场景消化不完积压时怎么处理

| gateway CPU 峰值 | 63.00% | 未单独采样（同量级） |
| postgres CPU 峰值 | 32.92% | **89.99%**（明显升高，见下面"下一个瓶颈"） |
| 数据库里最终处理完成（replied）数 | 12613（清空前）+ 已被清空丢弃 46887 条，见下方对账 | 17788（全部完成，未清空） |

**1 worker 的"发出数/ACK数/清空对账"**（Jo 已授权清空，清空前 messages_ready=47170、
messages_unacknowledged=32，清空后两者都是 0，数据库没有删任何数据）：
```
messages_acked = 59500（全部 accepted，app_duplicates=0、app_rate_limited=0）
数据库里这批实际处理完成（replied）= 12613
59500 − 12613 = 46887（被清空丢弃的实际数量）
Jo 给的清空前快照 47170+32=47202，与 46887 差 315
```
差额 315 的解释：worker 一直在以约 10/s 处理，从 Jo 读快照到真正执行清空命令之间隔了几秒
（估算约 30 秒），这段时间又消化掉了几百条，所以真正被清空时"就绪"的数量比快照读到的
47170 略少——不是漏算，是快照和清空动作之间的正常时间差。那 32 条"unacknowledged"没有被
清空丢掉（RabbitMQ 的 `purge_queue` 只清"就绪"消息，不动"已投递未确认"的），它们正常处理
完，已经算在 12613 里。**没有发生"发出去但没处理也没被算进任何一类"的情况**。

**跟题目指标（500 连接/200 msg/s/5 分钟）对比**：两种配置都不达标。1 worker 实测吞吐能力
约 10/s（约 5%），3 worker 约 37/s（约 18.5%，提升明显但仍远达不到 200/s）。

**结论**：worker 是单进程/单核 CPU 瓶颈，水平扩展 3 个副本后吞吐能力提升到约 3.7 倍（略超
线性），验证了架构设计（"worker 可水平扩展多实例"）在真实 LLM 负载下确实有效；但 3 副本下
Postgres CPU 已经从 33% 升到 90%，继续加副本，下一个瓶颈大概率是 Postgres（见后面专门一节）。

## 场景 4：LLM 超时率 20%（150 条连接，改为 30 msg/s，5 分钟，3 worker）

**为什么把速率从题目默认的"跑场景 1 的负载"（200/s）改成 30/s**（AGENT_LOG 记录了这个决定
的原因）：题目本身没有规定这个场景一定要用 200/s，"跑场景 1 的负载"只是准备阶段自己选的
默认值；场景 1 已经证明 3 worker 的真实处理能力约 37/s，如果继续用 200/s，跟场景 1/2/3 一样
会迅速堆出几万条积压，这个场景真正要验证的是"**降级行为本身对不对**"（超时会不会正确降级
成关键词规则、会不会触发熔断、系统会不会崩溃、会不会有消息卡住或进死信），不是"再测一次
吞吐量上限"（吞吐量上限场景 1 已经测过了）。改成 30/s（在 3 worker 处理能力之内，接近但不
超过），让系统能一边处理超时故障一边跟上速率，才能干净地观察到降级行为，而不是被同时压力

## 单 worker 吞吐上限（约 10/s）的原因分析

用直接探测法测量（向一个已有大量历史的会话单独发 15 条消息，前后取 `/metrics` 差值，排除
并发争抢干扰）：

```
worker_process_seconds（从队列取出到确认完成）：Δ=34.59s / 15 条 = 2.31s/条
worker_reply_seconds（respond() 本身，含流式生成）：Δ=27.88s / 15 条 = 1.86s/条
worker_first_token_seconds（真正走流式生成那部分）：Δ=2.78s / 9 条 = 0.31s/条
```
按 `worker_process_seconds`（单条 2.31s，无并发争抢下测得）和实测吞吐 10/s 反推，相当于
prefetch=32 的并发槽位里同时有约 23 条消息在处理，与 32 的上限量级相符。

**`meta.timings.respond` 有没有漏计流式输出时间**：**没有漏计**。同一个会话连续几条消息的
`respond_ms` 有时是几毫秒、有时是 2000~4400 毫秒：
```
respond_ms  classify_ms  route_source
3025.5      322.4        llm
4127.2      329.8        llm
1.8         324.1        llm
2138.5      330.6        llm
```
这是因为 mock-llm 按约 30ms/字（约 33.3 字/秒，`mocks/mock_llm/main.py` 的
`asyncio.sleep(0.03)`，见下面"mock 耗时 vs 系统自身耗时拆分"一节的 git 查证）真实流式吐字，
回复短（几个字）几十毫秒内吐完，回复长（一两百字）就要吐 3~6 秒，`timings.respond` 精确
记录了这整段耗时，包含流式输出。之前报告里贴的"respond 只有 11.9ms"只是抽到了短回复的
样本，不代表这个字段本身有问题。

**回复发完之后同步生成摘要，不计入 `meta.timings` 任何字段**——这是真实存在的一个"看不见"
的耗时来源：`app/worker/handler.py:232` 的 `await maybe_update_summary(...)` 是在
`respond()` 返回、reply_end 已经发给客户端之后，`message.ack()` 之前同步执行的，条件满足
（未覆盖消息数超过 `CONVERSATION_HISTORY_LIMIT=10`）时会真的再发起一次 LLM 调用生成摘要，
这次调用的耗时不会出现在 `meta.timings` 的任何键里。这次 15 条消息的直接探测没有测到明显的
额外残差（1.86s respond + 0.45s classify ≈ 2.31s，跟测到的 process_seconds 基本对得上），
说明这批里摘要生成没有显著叠加，但不代表它在触发时不会叠加——它有自己的预算检查和真实网络
往返，条件满足时一样要多等一次。**这是一个真实的可观测性缺口**：`meta.timings` 应该但目前
没有单独记一个 `summary` 键，留作后续改进项，本轮不改代码。

**CPU 打满主要耗在哪**：有证据支持推测，但**没有做逐函数 CPU profiling（没跑
py-spy/cProfile），不能精确到百分比**。证据链：单条消息的耗时主体是"等 mock-llm"（网络
等待，本身不占 CPU）；但 worker CPU 持续钉在 92~110%。合理机制：mock-llm 按小块/字符
流式吐字，每次吐一点，worker 就要醒一次去跑 OutputGuard 分句缓冲、正则核对出处、必要时发
Redis publish、写结构化日志——单次很便宜，但 prefetch=32 时多条消息同时在流式吐字，这类
"醒来处理一小块"的事件频率很高，累加起来吃满单核是合理的解释，但没有直接测量证实具体是哪
几行代码占了多少 CPU，如实说明局限性。

## 下一个瓶颈：Postgres

场景 1 从 1 worker 到 3 worker，postgres CPU 峰值从 32.92% 跳到 89.99%；场景 2/3/4（都是
3 worker）postgres CPU 峰值分别是 78.71%/75.40%/92.56%，全部明显高于 1 worker 时的水平。
Worker 连接池是 `pool_size=10, max_overflow=10`（`app/common/db.py`），每个 worker 进程
独立维护自己的连接池，3 个 worker 理论最多同时开到 60 个数据库连接；每条消息的处理路径里至少
有：读取历史消息、写入 user/assistant 两行、可能的摘要读写（2 次 SELECT + 1 次 upsert）、
llm_usage 记账（1 次 INSERT+commit）——多个 worker 副本并发时这些查询会互相排队。**如果继续
增加 worker 副本数（比如 5~10 个）去逼近题目的 200/1000 msg/s 目标，下一个会先顶到天花板的
大概率是 Postgres，不是 worker CPU**，建议下一步验证方向：加大连接池、给高频查询加索引/
减少往返次数、或者给 Postgres 单独扩容（更多 CPU 或者读写分离），而不是无限加 worker 副本数。

## mock 耗时 vs 系统自身耗时拆分，解释阶段一"完整回复 3004ms"

**先更正一个错误前提**：上一版这里写"mock-llm 每秒约 50 字，阶段一那条回复约 135 字"，
是用当前 `docs/PHASE4.md` 关键设计决定 7 里写的目标速度倒推的，这个前提不成立。用
`git log`/`git show` 查证：

- **逐字流式的间隔**：`mocks/mock_llm/main.py` 的 `_stream_text_chunks()` 里
  `await asyncio.sleep(0.03)`（每个字之间隔 30ms，相当于约 **33.3 字/秒**，不是 50）。
  用 `git log --follow -p -S "asyncio.sleep(0.03)" -- mocks/mock_llm/main.py` 查，这一行
  从 `ef7b4a3`（步骤 1.5 mock 服务，阶段一）引入后**从未被修改过**，包括
  `ad521e1`（阶段四 4.1）在内，历次改动都没有碰过这一行。
- **首字延迟**：`_config["latency_ms"]` 默认 300（`MOCK_LLM_LATENCY_MS=300`），同样从
  `ef7b4a3` 引入后未变过（`git log -p --follow -- .env.example | grep MOCK_LLM_LATENCY_MS`
  查证，历次 diff 里这一行只在 `+` 新增时出现过一次，此后从未再被改写）。
- **PHASE4.md"每秒约 50 个字"这句话**是在 `ad521e1`（阶段四 4.1）这次提交里新写进设计文档的
  （`git log --oneline -S "每秒约 50 个字" -- docs/PHASE4.md` 只查到这一次），但**这次提交
  完全没有改动 `mocks/mock_llm/main.py`**（`git show --stat ad521e1 -- mocks/mock_llm/` 无
  输出）——也就是说 4.1 改的是**文档描述的目标速度**（写了"50字/秒"这个设计意图），不是代码
  实际速度，代码这边的真实速度（33.3 字/秒）从阶段一到今天完全没变过，文档和代码在这一点上
  本身就有一处不精确（属于既有的小文档偏差，不是本轮改动引入的，这里指出但不在本轮改代码）。

**阶段一和现在的差距，真正原因是回复内容变了，不是速度变了**——两次都发送
`scripts/demo.sh` 里同一句话"你好，我想咨询一下课程安排"：

- **阶段一**（`ef7b4a3` 步骤 1.5）：那时候 LangGraph/意图路由都还没做（是阶段二才有的），
  mock-llm 收到任何请求都固定返回同一段模板文本：
  ```
  您好，我已经收到您的问题，正在为您查询处理，请稍等。根据目前掌握的信息，建议您可以先
  查看课程详情页，或者联系人工客服获取更详细的帮助。如果还有其他问题，请随时告诉我。
  ```
  这段文本是 **83 个字**。按 300ms 首字延迟 + 83×30ms=2490ms 流式输出 = 2790ms 的
  mock 耗时，加上阶段一那套更简单的处理流程自己的开销，跟实测的"首 token 耗时=491.1ms、
  完整回复耗时=3004.2ms"吻合（491.1ms 首字里含 300ms 延迟 + 约 191ms 的系统开销；
  3004.2−491.1=2513.1ms 的流式时间 ÷ 30ms/字 ≈ 83.8 字，跟模板的 83 字几乎精确对上）。
- **现在**（重新跑了一次 `make demo` 验证）：同一句话被"问候规则"拦下，路由成
  `intent=chitchat`，LLM 真实生成了一句短回复"好的，我在。你可以直接说你的问题。"
  （**17 个字**），`meta.timings` 精确记录：
  ```json
  {"route_source": "llm", "llm_ms": 1134.0,
   "timings": {"load_context": 4.1, "classify": 326.2, "chitchat": 9.9, "respond": 836.4}}
  ```
  respond 阶段 836.4ms ≈ 300ms 首字延迟 + 17×30ms=510ms 流式输出 = 810ms（含少量 guard
  处理开销），加上 classify 的 326.2ms，总共约 1176.6ms，跟实测"首 token 耗时=848.5ms、
  完整回复耗时=1226.6ms"吻合（Jo 提到的 1201ms 是同一量级，属于正常的几十毫秒次跑波动）。

**结论**：mock-llm 的流式速度（33.3 字/秒）和首字延迟（300ms）从阶段一到现在**从未改变**；
阶段一"3004ms"和现在"约 1201~1227ms"的差距，完全是因为**同一句输入在两个时间点被路由到了
不同长度的回复**（阶段一固定模板 83 字 vs 现在问候规则短回复 17 字），不是 mock-llm 变快了。
这跟本轮压测反复验证到的模式完全一致：**respond 阶段耗时和回复长度成正比**（见"单 worker
吞吐上限"一节），不是系统处理变慢或变快。
