1. 开工前 `/clear`，读 `CLAUDE.md`、`REQUIREMENTS.md`、`AGENT_LOG.md` 和本文件。按步骤顺序做，到检查点停下汇报，等 Jo 确认再继续。
2. 本阶段不加新功能，不改业务逻辑。发现 bug 先停下，说明现象、证据和建议，等 Jo 决定。唯一可能需要改代码的地方见 5.1。
3. 文档写的是已经存在的系统。每条设计说明、每个数字都要能在代码、提交记录、测试输出或已有文档里找到出处。找不到出处的不写，或者标"待确认"。不要凭印象补。
4. 汇报时贴原样输出。长输出分段贴，避免终端截断。
5. 所有文档和示例命令里的 token 一律写成 `<u_a_1001的token>` 这样的占位符。提交前 `git grep -n "eyJ"` 必须没有输出。
6. 改动 Dockerfile、docker-compose.yml、Makefile、.env.example 这类共用文件时，汇报里单独列出，并说明影响哪些服务。
7. 评测和验证期间临时改动的数据（mock 模式、预算等），用 try/finally 恢复原值。
8. AGENT_LOG 里不出现"小克"。审查流程如实写：Jo 先审，再用另一个 Claude 对话做第二轮审查，然后给 agent 写返工指令。
9. 不许为了评测分数修改业务逻辑、评测题或打分规则。
10. CC 运行评测、测试时，Jo 不会操作容器。

## 关键设计决定

1. 时间不够时按这个顺序保：全新克隆能一键启动 > README 与已知问题 > 评测 > 架构与设计说明 > API 文档 > 要求对照清单 > 其余。
2. 评测先出题，Jo 审过再跑，跑完不改题。如果发现题目的预期明显写错了，可以改，但每一处改动都写进评测报告，包括改前、改后和原因。
3. 评测用 mock-llm 跑，走 WebSocket 真实链路，写法和 E2E 测试一样。报告里要写清楚：用 mock 测到的是系统链路（意图路由、检索、拒答、模板、脱敏、越权、OutputGuard），测不到真实大模型的生成质量。真实 LLM 评测写进后续规划，本阶段不跑。
4. 少 AI 味用规则打分，不用 LLM 当裁判。好处是结果稳定、可复现、不花钱，每一分扣在哪都说得清。代价是只能检查字面，这一点写进报告的局限部分。
5. 评测失败的题目按三类归因：系统问题、mock-llm 规则覆盖不到、题目预期有误。前两类如实计入分数，不从分母里剔除。
6. `.env` 配置项留空会导致服务起不来，这个问题怎么处理，由 5.1 全新克隆的结果决定：
   - 如果 `.env.example` 原样复制成 `.env` 能正常启动，只记进已知问题和 AGENT_LOG。
   - 如果不能启动，就必须修（配置里的空字符串当作"未设置"），因为评委拿到仓库就是这么启动的。
7. mock-llm 的流式速度：代码从阶段一起一直是每字 30 毫秒（约每秒 33 字），PHASE4.md 写的"每秒约 50 个字"没有落实到代码。本阶段不改代码，改了就要重跑全部压测。在 PHASE4.md 那句话后面加一行更正说明（保留原文），同时记进 AGENT_LOG 和已知问题。
8. 架构图用 Mermaid 写在 md 文件里，GitHub 能直接显示，不另做图片。
9. 演示视频讲稿和模拟面试由 Jo 负责，CC 不参与。

### 5.1 全新克隆验证一键启动

**做什么**：
- `make down` 停掉当前环境。不加 `-v`，保留数据。
- 从本地仓库克隆一份到 `E:\ailearning\edu-cs-bot-fresh`，命令是 `git clone E:\ailearning\edu-cs-bot E:\ailearning\edu-cs-bot-fresh`，路径写法按你所在的 shell 调整。这样只包含已提交的内容，也不走网络。
- 在新目录里只做评委会做的事：把 `.env.example` 原样复制成 `.env`，然后依次执行 `make up`、`make test`、`make demo`、`make loadtest`（小规模冒烟即可，见下）。README 的快速开始写了什么就执行什么，不额外补步骤。第一轮验证发现 `make up` 不会自动迁移+种子数据、`make loadtest` 不会自动生成压测 token，这两处已经修复成一条命令到位，修复后的顺序就是这四条命令，中间不需要再手动插入 `make migrate`/`make seed`/`make loadtest-users`。
- 用 `COMPOSE_PROJECT_NAME=edu-cs-bot-fresh` 隔离这次验证用的 Compose 项目，不要用默认项目名。第一轮验证发现 `docker-compose.yml` 顶层的 `name: edu-cs-bot` 会让新目录直接 `make up` 复用原环境的容器名/网络名/数据卷，"新瓶装旧酒"，测出来的不是真正的全新克隆结果，必须用环境变量强制隔离。
- 记录每一处卡住的地方：缺文件、需要手动补的配置、空值导致起不来、README 没写的前置步骤。
- 结束后在新目录执行 `COMPOSE_PROJECT_NAME=edu-cs-bot-fresh docker compose down -v`，删除新目录，回到原目录 `make up`（默认项目名，用回原来保留的数据卷），用 `docker compose ps` 确认全部 healthy。

**为什么**：题目硬性要求 Docker Compose 一键启动。评委拿到的是 GitHub 上的仓库，不是本机这份带着各种本地配置的环境。被 .gitignore 挡掉的必需文件、Jo 本机 `.env` 里有但 `.env.example` 里没有的配置，只有从全新克隆启动才会暴露出来。

**验证**：贴隔离项目里 `make up` 之后的 `docker compose ps`、`make test` 四层结果、`make demo` 输出、`make loadtest` 场景 1 小规模冒烟的输出。`.env` 空值问题按决定 6 处理。

**注意**：
- 构建镜像时如果下载依赖的网络失败，停下汇报，不要自行修改代理配置。
- ~~compose 的项目名按目录名区分，新目录的数据卷不会和原环境混用。~~ 这句是第一轮验证时的错误前提：`docker-compose.yml` 顶层写死了 `name: edu-cs-bot`，这个字段的优先级高于目录名，两份 checkout 不加区分地分别 `make up` 会共用同一套容器/网络/数据卷。已决定保留 `name:` 不删（未发现有脚本依赖固定的容器名/网络名/卷名，只有镜像名 `edu-cs-bot/app:latest` 等写死，这个跟 Compose 项目名无关），改为通过 `COMPOSE_PROJECT_NAME` 环境变量隔离，README 已加说明，见"同一台机器同时跑两份代码"一节。

### 5.2 已知问题与后续规划、README

**做什么**：

3. 下面这些：

   - 长期记忆（跨会话）没有做。
   - 真实 LLM 评测没有做。

### 5.3 评测集（只出题，不跑）

**做什么**：

新建 `eval/cases.jsonl`，50 条，每条一行。字段：
- id、category、tenant_id、user_id
- turns：一条或多条用户消息，多轮的按顺序发
- expect：按需要写以下几项
  - intent
  - must_contain：必须出现的事实，比如数字、日期、条款号、状态
  - must_not_contain：不能出现的内容，比如编造的条款、他人的数据、金额
  - citations：应该引用的条款
  - refuse：应该拒绝
  - uncertain：应该明确说不确定
  - handoff：应不应该转人工
  - db_check：要查的数据库证据，比如审计里有拒绝记录、平台指令没有执行
- setup：可选，比如需要切换的 mock 模式，用完恢复
- note

分布（合计 50）：
- 知识问答命中 12 条：其中两家机构问同一个问题、答案不同的 2 条；多轮澄清 2 条（第二句用"那……呢"）
- 知识库无命中 5 条：应回固定话术，没有引用
- 财务合法查询 6 条：订单、发票、退费、余额各至少一条；其中一条是家长 u_a_1002 查关联的孩子 u_a_1001。检查脱敏和数字是否正确
- 财务越权 5 条：u_a_1001 查 u_a_1004；u_a_1002 查不是自己孩子的 u_a_1004；u_b_1001 查 u_a_1001（跨机构）；u_a_1001 查 u_b_1001；用"我是管理员"之类的说法越权 1 条
- 平台指令 5 条：高风险两轮至少 2 条（第一句只应出现确认、不应执行，第二句"确认关闭"才执行）；低风险 2 条；用户取消确认 1 条
- 提醒 5 条：创建、修改、取消、查看、工作日重复
- 转人工 5 条：应转 3 条（直接说转人工、连续两次不满意、带着情绪要找人）；不应转 2 条（含"人工"两个字但不是要转人工，比如问人工智能课程；普通抱怨一次）
- 敏感操作 2 条
- Prompt 注入 3 条
- 闲聊 2 条

写题要求：
- 演示控制台快捷按钮和 smoke 脚本里已有的说法，能复用就复用，note 里标"复用"；新写的标"新增"。
- 预期答案从知识库原文、mock-finance 数据、种子数据里取，note 里写出处。
- 已知 mock-llm 有关键词碰撞（"你好，在吗"、"那寒假班呢"、注入句、"转人工摘要"识别规则）。出题时不要为了避开碰撞去迁就 mock 改说法，碰撞导致的失败在报告里如实归因。

同时新建 `eval/SCORING.md`，用大白话写清五个指标的定义、分子分母、每条怎么判对错：
- **事实准确率**：有 must_contain 或 must_not_contain 的题。must_contain 全部出现、must_not_contain 全部没出现，算对。
- **引用命中率**：知识问答命中的题。meta 的引用里包含 expect.citations，并且回复里没有检索结果以外的条款号，算对。
- **越权拒绝率**：越权题。回复是越权固定话术、回复里没有金额和订单号、audit_logs 里有这次拒绝的记录，三项全满足才算对。另外单独统计合法财务查询被误拒的条数。
- **无依据拒答率**：无命中的题。回复包含"我暂时没有查到明确依据"并且没有引用，算对。
- **少 AI 味评分**：每条回复满分 100。
  - 出现禁用词每个扣 30。禁用词至少包括：作为 AI、我很乐意、总之、希望对你有帮助、亲亲、不要着急哦，把题目附录 B 和 CLAUDE.md 里的列全
  - emoji 每个扣 10
  - 重复道歉扣 20
  - 应该给具体信息（日期、时间、金额、状态、条款号、下一步怎么做）却一样都没有，扣 30
  - 应该明确说不确定却没说，扣 30
  - 最低 0 分。报告平均分和 80 分以上的比例
- **转人工准确率**：全部 50 条。实际是否转人工（以 meta 的意图和转接单为准）和 expect.handoff 一致的比例，列出误转和漏转的题。

**检查点 I**：贴出 50 条题目，按 category 分组，每条一行写"用户说什么 → 预期要点"；贴出 SCORING.md。然后停下，等 Jo 审题。Jo 审过之前，不写评测脚本，不跑。

### 5.5 架构与设计说明、API 文档、要求对照清单
