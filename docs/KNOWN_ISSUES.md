# 已知问题与后续规划

每条写四项：**现象**、**影响**、**为什么没做**、**后续怎么做**。来源三个：`AGENT_LOG.md`
里记录的已知问题、各阶段文档里砍掉/简化的内容、本阶段（五）新发现的局限。写"为什么没做"是
为了证明这是权衡过的取舍，不是漏掉了——老板/评委追问"哪里没做好"时，这份文档就是答案。

## 运行环境

### 1. 只在 Windows + Docker Desktop 上测试过

**现象**：开发和测试机器是 Windows 11 + Docker Desktop，i7-12650H（10 核 16 线程）、16GB
内存、512GB NVMe。Linux/macOS 从未实际跑过 `make up`/`make test`。

**影响**：如果评委在 Linux/macOS 上跑，理论上应该没问题（`docker-compose.yml`、`Makefile`、
Dockerfile 里没有 Windows 专属写法，`.sh` 脚本按 CLAUDE.md 硬性规则统一 LF 换行），但没有
实测验证过，不能保证 100% 没有平台差异（比如文件权限、路径大小写敏感性）。

**为什么没做**：条件所限，手头只有一台 Windows 开发机。

**后续怎么做**：拿到 Linux/macOS 机器后跑一遍 5.1 的全新克隆验证流程，把结果补进这里。

### 2. Docker Desktop 默认只分给容器约 7.6GB 内存

**现象**：`docker info` 查到 Docker Desktop 分给容器的资源是 16 CPU / 7.6GiB 内存，不是
宿主机全部的 16GB。

**影响**：压测报告（`docs/LOADTEST.md`）里的所有数字都是在这个资源上限下跑出来的，不是
宿主机满血状态；如果评委的 Docker Desktop 分配了更多/更少内存，压测数字会不一样。

**为什么没做**：默认配置就是这样，没有手动调大，因为调大之后的数字就不能代表"大多数人拿到
这个仓库、不特意调 Docker 设置"时的真实体验。

**后续怎么做**：如果要验证"给更多资源会不会解除 worker CPU 瓶颈"，可以调大 Docker Desktop
的资源上限重跑压测场景 1 对比，本阶段没有做这个对比实验。

### 3. `.env.example` 里部分配置项留空

**现象**：`REDIS_PASSWORD`、`DEFAULT_DAILY_TOKEN_BUDGET` 等几项在 `.env.example` 里默认
是空字符串。

**影响**：实测（5.1 全新克隆验证）不影响启动——`REDIS_PASSWORD` 留空表示不需要密码；
`DEFAULT_DAILY_TOKEN_BUDGET` 留空表示不限额，这是代码里的合法取值（`0b11be3` 那次提交已经
把"空字符串当成未设置"这个解析问题修过），不是配置遗漏。

**为什么没做**：不需要做——按 `docs/PHASE5.md` 决定 6，验证结果是"原样复制能正常启动"，
只需要记录，不需要改代码。

**后续怎么做**：无需处理；以后新增必填的配置项时，要重新走一遍全新克隆验证，确认空字符串
不会导致启动失败。

### 4. `docker-compose.yml` 顶层写死了 `name: edu-cs-bot`

**现象**：同一台机器上如果有两份 checkout（比如再 clone 一份做对比测试），直接分别
`make up` 会共用同一套容器名/网络/数据卷，互相覆盖，没有报错提示。5.1 全新克隆验证第一轮
就因为这个问题，误把"复用了原环境数据"的结果当成了"真正的全新克隆"结果。

**影响**：仅限"同一台机器同时跑两份代码"这个场景，正常的单份 checkout 不受影响。

**为什么没做**：检查过没有任何脚本/CI/Makefile 依赖这个固定项目名（只有镜像名
`edu-cs-bot/app:latest` 等写死，跟 Compose 项目名是两回事），删掉 `name:` 风险很小，但 Jo
审查后决定保留，改用 `COMPOSE_PROJECT_NAME` 环境变量隔离（见 README"同一台机器同时跑两份
代码"一节），不改配置文件本身。

**后续怎么做**：无需处理，已有文档化的绕开方法。

## mock 服务的固有局限

### 5. mock-llm 用确定性关键词规则模拟真实 LLM 的判断力

**现象**：`mocks/mock_llm/rules.py` 靠关键词/正则表匹配来决定路由到哪个工具，这类"表面
匹配"在开发过程中反复撞上意料之外的碰撞——"你好，在吗"因为带"吗"字被问句特征词规则误判成
知识问答（2.7）、"忽略之前所有规则"的注入文本因为"规则"这个词同时出现在排除词表和问句特征
词表里被误判（2.9）、"转人工摘要"识别靠字符串匹配（2.12）。日程提醒规则也只认关键词+正则
拼出来的有限说法，不认识"周三""下周一"这类具体星期几的口语表达。

**影响**：这类碰撞每次被发现都已经修复，不是遗留的 bug；但这说明只要新增测试句子用词跟已有
规则表重叠，就可能出现新的碰撞，5.3 评测集出题时已经注意规避、复用已验证过的句子。

**为什么没做**：这是"用规则模拟大模型"这个设计本身的代价，接真实 LLM 之后这类碰撞会自然
消失（真实 LLM 靠语义理解，不是关键词匹配）。

**后续怎么做**：接入真实 LLM（DeepSeek）后不需要改任何路由逻辑，问题自然消失；在那之前，
5.3 评测集的"少 AI 味评分"等指标标准里已经写明"已知 mock-llm 有关键词碰撞...出题时不要为了
避开碰撞去迁就 mock 改说法，碰撞导致的失败在报告里如实归因"。

### 6. mock-llm 生成的摘要/转人工摘要是固定文案，测不出真实质量

**现象**：`mocks/mock_llm/rules.py` 对历史摘要生成、转人工摘要生成两类请求都返回同一句
固定模板文本，不会真的根据对话内容生成描述。

**影响**：能验证"摘要生成→存库→下一轮读取拼回"这条链路走得通、失败时的兜底和脱敏，但不能
验证摘要内容是否真的准确、有没有遗漏关键信息——这件事本质上属于"真实 LLM 生成质量评测没有
做"（见下面第 16 条），这里单独点出摘要这个具体场景。

**为什么没做**：mock-llm 是确定性假服务，不该也不能去"理解"对话内容生成真实摘要。

**后续怎么做**：接真实 LLM 后专门评测摘要质量（准确率、有没有遗漏关键信息），本阶段的
5.3/5.4 评测集用 mock-llm 跑，测不到这一层。

### 7. 检索用哈希向量，不懂同义词

**现象**：`EMBEDDING_PROVIDER=hash`（阶段二 1.5，确定性哈希向量，不依赖网络/模型）本质上
是字面匹配的变体，"退款政策"查不到"退费政策"这类同义词场景会因为分数不够而判定为"没查到"。
`docs/phase2_threshold.md` 的标定记录里也踩到过一次：t_b 用 t_a 的说法"老带新奖励多少课时"
提问，分数比好几条不该命中的问题还低，因为 t_b 的活动文档用的是"推荐有礼"这个完全不同的
名字。

**影响**：遇到同义词场景，系统回"暂时没有查到明确依据"，这个行为本身是**对的**（不编造），
但体验上不如真正理解语义的向量模型。E2E 场景 10（知识库无命中）验证的正是这个行为。

**5.4 评测补充发现的另一面（假阳性，不只是假阴性）**：这条局限原来只讲"该命中的没命中"，
5.4 评测跑真实 pgvector 检索时还发现了反过来的情况——"不该命中的命中了"：`nohit04`
"课程费用包含教材费吗？"检索到《课程服务协议》3.1 条"课程费用以下单页面显示的金额为准"
（分数 0.366，高于 `KNOWLEDGE_MIN_SCORE=0.30`），`nohit05`"上课需要交押金吗？"检索到
《常见问题》Q7 设备要求那条（分数 0.3091），两条都跟问题字面上没有任何关键词重合，纯粹是
哈希向量凑巧算出的相似度超过了阈值。也就是说哈希向量的不准确是双向的：既会漏掉真正相关但
措辞不同的条款，也会在没有语义关联的情况下偶然给出一个不相关的条款、让系统"煞有介事"地
引用一条答非所问的依据——这比"查不到"更容易误导用户，因为回复看起来是有出处的。

**为什么没做**：阶段二的既定设计（决定见 `docs/PHASE2.md`），确定性哈希向量不依赖外部模型/
网络，代价是没有语义理解能力；`RETRIEVER=mock_knowledge` 这个备用检索器同样是字面匹配的
变体，两种检索器打分尺度不同，标定后发现两组分数无法完全分开，取的是"宁可漏判不误判"的止损
值（`MOCK_KNOWLEDGE_MIN_SCORE=0.04`），Jo 审查后确认这个止损值可以接受，不必投入时间把
mock_knowledge 的打分方式调到跟 pgvector 一样精确。

**后续怎么做**：换成真正的语义 embedding（比如接入真实 embedding 模型的 API）能解决同义词
问题，需要额外的网络依赖和成本，本阶段范围内不做。

### 8. mock-finance/mock-platform 之外的故障覆盖有限

**现象**：19 种故障注入（题目 6.5）里，只亲手做了题目点名的 8 种，另有 3 种由 E2E 测试
自动覆盖，其余 8 种只写了注入和恢复命令（`docs/FAULT_INJECTION.md`），没有亲手跑一遍看
现场反应。

**影响**：写了命令的这 8 种理论上应该能用同样的方式验证，但没有实际跑过、没有记录过实际
现象，不能保证跟预期完全一致。

**为什么没做**：时间分配优先级，题目明确点名的场景优先验证。

**后续怎么做**：`docs/FAULT_INJECTION.md` 已经列出了每一种的注入/恢复命令，需要时照着跑
一遍即可，不需要额外开发。

## 观测与运维的已知缺口

### 9. `meta.timings` 缺一个 `summary` 键

**现象**：回复发完之后同步生成历史摘要（`maybe_update_summary`，`app/worker/handler.py`）
的耗时不计入 `meta.timings` 任何字段，是一个真实的可观测性缺口。见 `docs/LOADTEST.md`"单
worker 吞吐上限"一节。

**影响**：条件满足（未覆盖消息数超过 `CONVERSATION_HISTORY_LIMIT`）时会真的再发起一次 LLM
调用，这次调用的耗时"看不见"，压测报告和演示控制台的耗时数字都会略微低估。

**为什么没做**：发现得晚（压测复盘时才发现），补埋点要改 `app/worker/handler.py`，超出
本阶段"不改业务逻辑"的范围。

**后续怎么做**：给 `maybe_update_summary` 包一层跟 `_timed()` 类似的计时，加一个 `summary`
键写进 `meta.timings`。

### 10. CPU 打满的具体归因没有做逐函数 profiling

**现象**：`docs/LOADTEST.md` 有间接证据支持"mock-llm 流式吐字导致高频小事件"这个推测，但
没有跑 py-spy/cProfile 实测，不能精确到具体哪几行代码占了多少 CPU。

**影响**：知道瓶颈在 worker 单核 CPU，但不知道具体优化哪个函数收益最大。

**为什么没做**：压测本阶段的目标是"测出瓶颈在哪一层"，不是"优化到达标"，题目要求的是压测
报告，不是性能调优报告；压测本身也没有做调优验证（改连接池大小、加索引等都只是根据 CPU/
观测数据提出的建议方向，没有实际改代码验证效果）。

**后续怎么做**：跑一次 py-spy 采样压测期间的 worker 进程，定位具体热点函数；然后针对性
优化（比如 OutputGuard 分句缓冲、结构化日志序列化）并重新压测对比。

### 11. gateway 的 `redis_unavailable` 告警不带 `trace_id`

**现象**：`app/common/redis.py` 的 `raise_alert("redis_unavailable")` 触发时没有绑定
当前请求的 `trace_id`。

**影响**：排障时看到这条告警，没法直接关联到是哪条消息触发的（虽然 Redis 故障通常是全局性
的，不是某一条消息独有的问题，实际排障影响不大）。

**为什么没做**：没有专门排查这是不是有意为之的设计（Redis 故障本身跟具体某条消息无关，
`trace_id` 语义上可能不适用）——本阶段没有深入这个问题。

**后续怎么做**：确认 Redis 故障告警是否需要绑定触发它的第一条请求的 `trace_id`，需要的话
在 `note_redis_result()` 调用处传入当前 `trace_id`。

### 12. worker 日志被大量 `GET /health` 淹没

**现象**：worker 健康检查探针（`/health`）每 5 秒被 Docker 调用一次，每次调用都会在
worker 的结构化日志里留下一条记录，正常业务日志被这些健康检查日志淹没，翻日志找真正的业务
事件比较费劲。

**影响**：不影响功能，只影响排障时的日志可读性。

**为什么没做**：发现较晚，改动涉及日志中间件/uvicorn access log 配置，本阶段没有优先处理。

**后续怎么做**：给 `/health` 路径单独关掉 access log（uvicorn 支持按路径过滤），或者把
健康检查日志降级成 `DEBUG` 级别，默认不输出。

### 13. 死信前的 3 次重试之间没有等待间隔

**现象**（PHASE3.md 预设的已知问题，落地验证后确认符合）：`DLQ_MAX_RETRIES=3` 次重试之间
没有退避等待，4 次尝试在 3 秒多一点之内就全部打完。

**影响**：数据库短暂抖动一下（比如几秒的连接波动）就可能把一条消息在几秒内打进死信，没有
给"抖动过去就自愈"留出等待窗口。

**为什么没做**：PHASE3.md 设计阶段就接受了这个简化，重试间隔涉及消息重新入队的时机控制，
跟"重试次数上限"这个硬性规则的核心要求（禁止无限重试）相比优先级更低。

**后续怎么做**：给 `x-retry-count` 判断加一个基于重试次数的延迟（比如重新发布消息前
`sleep`，或者用 RabbitMQ 的延迟交换机/TTL+死信队列做延迟重试）。

### 14. 熔断状态每个 worker 进程独立维护，不跨实例共享

**现象**（PHASE3.md 预设的已知问题）：`app/common/circuit_breaker.py` 的熔断状态放在
进程自己的内存里，不放 Redis。开 3 个 worker 时，同一个 LLM 故障要让 3 个 worker 各自攒够
`CB_FAILURE_THRESHOLD`（5）次失败才会都打开熔断，中间那几秒还是会有请求打到已经挂了的
上游。压测第二轮（场景 4）实测验证过：worker-1/2/3 各自的
`worker_circuit_breaker_state{service="llm"}` 确实是分别独立变化的。

**影响**：多副本场景下熔断保护有短暂的不一致窗口，不是立即全体生效。

**为什么没做**：跨实例共享熔断状态需要引入 Redis 作为状态存储并处理并发更新，复杂度和收益
不成正比——客服场景下这个"几秒钟不一致窗口"的实际影响很小。

**后续怎么做**：如果要做，把熔断状态从进程内存挪到 Redis（比如用 `INCR`+过期时间实现滑动
窗口计数），所有 worker 副本共享同一份状态。

### 15. 告警不接真实通道（钉钉/邮件/短信）

**现象**（PHASE4.md 关键设计决定第 5 条本身就这么定的）：三处告警触发点（LLM/finance 熔断
打开、Redis 不可用）都只做到"结构化日志 + Prometheus 计数器"，`raise_alert()` 没有接任何
真实的通知通道。

**影响**：告警只能靠人主动看日志/Grafana（也没做，见下一条）才能发现，不会主动推送给人。

**为什么没做**：题目本身没有要求接真实告警通道，PHASE4.md 设计阶段就明确了范围。

**后续怎么做**：`raise_alert()` 已经是所有告警的统一入口，接真实通道只需要改这一个函数
（比如调钉钉机器人 webhook），不需要改调用方。

### 16. 数据没有定时备份

**现象**：PostgreSQL 数据只放在 Docker 数据卷 `postgres_data` 里，没有配置任何定时全量/
增量备份（`pg_dump`）或 WAL 归档。RabbitMQ 已经确认是持久化的：`app/common/mq.py` 声明
交换机/队列都带 `durable=True`（`im.inbound`→`inbound.messages`、`im.dlx`→`inbound.dead`
两组都是），`app/gateway/message_handler.py` 和 `app/worker/consumer.py` 发布消息时都带
`delivery_mode=aio_pika.DeliveryMode.PERSISTENT`，消息本身会落盘到 `rabbitmq_data` 卷、
跟着容器重启能恢复，但这只是"进程重启不丢"，不是"卷本身损坏/被误删也能恢复"意义上的备份。

Redis 里存的都是可重算的缓存/计数类数据，逐一核实过用途和丢失后果：
- `dedup:{tenant_id}:{message_id}`（`app/gateway/message_handler.py`，`SET NX EX`，TTL=
  `dedup_ttl_seconds` 默认 86400 秒）：去重记号。丢失后果：网关层的去重窗口失效，但
  `messages` 表的 `(tenant_id, message_id)` 唯一约束还有兜底（CLAUDE.md 硬性规则"队列至少
  一次投递 + 数据库唯一约束"设计的本意就是防这种情况），不会真正产生重复业务记录。
- `ratelimit:user:{tenant_id}:{user_id}` / `ratelimit:tenant:{tenant_id}`（`app/common/
  rate_limit.py`，INCR+EXPIRE 的 Lua 脚本，窗口分别是 10 秒/1 秒）：限流计数器。丢失后果：
  计数清零重新计，短暂时间内可能放过一些原本要被限流的消息，不会导致数据错误。
- `llm:budget:{tenant_id}:{YYYY-MM-DD}`（`app/common/llm_usage.py`，TTL 2 天）：机构当天
  已用 token 数。丢失后果：当天已用量清零，机构可能在预算耗尽前多用一些 token（多花一点
  成本），不会导致业务数据损坏。
- `im:out:{tenant_id}:{user_id}` 频道（`app/worker/pubsub.py`/`app/scheduler/pubsub.py`
  发布，`app/gateway/connection_manager.py` 订阅）：这个不是"存储"，是 pub/sub 消息总线，
  设计上本来就不持久化——如果消息发布时刚好没有 gateway 实例在订阅（比如 Redis 短暂重启），
  这条推送会丢，但回复内容已经写进 `messages` 表（权威数据源），用户刷新页面/重连能重新
  拉到，不属于"数据丢失"。

**影响**：如果宿主机磁盘损坏、Docker 数据卷被误删，或者需要回滚到"昨天"这类任意时间点，
现在没有任何手段恢复 `postgres_data` 里的业务数据（租户、用户、会话、消息、审计日志、
提醒、token 用量流水等）——这是生产环境的真实风险点，评委/面试官问"数据怎么备份"时要如实
说明目前没做。

**为什么没做**：题目本身没有点名要求数据库备份方案，各阶段 PHASE 文档也没有把这个列进
范围，本地开发/演示环境的优先级一直排在功能实现之后。

**后续怎么做**：给 PostgreSQL 加一个独立的 `pg_dump` 定时任务（比如另起一个轻量容器，
`cron` 每天全量转储到宿主机挂载目录或对象存储），再开启 WAL 归档（`archive_mode=on` +
`archive_command`），配合基础备份可以恢复到任意时间点（PITR）；RabbitMQ/Redis 都是可
重算的中间态数据，不需要额外的备份方案，现状已经足够。

## 题目允许但本阶段没做的能力

以下几项是各 PHASE 文档里明确讨论过、评估后决定不做或简化的内容：

### 17. 真实 LLM 质量评测没有做

**现象**：5.3/5.4 的评测集全部用 mock-llm 跑，走真实 WebSocket 链路，测的是系统链路（意图
路由、检索、拒答、模板、脱敏、越权、OutputGuard），测不到真实大模型的生成质量、语言是否
自然、摘要是否准确贴合对话内容。

**影响**：拒答/越权/引用这类"对不对"的判断能测，但"答得好不好"这类需要真实语言理解的维度
测不到。

**为什么没做**：题目允许"可以使用真实 LLM 做演示，但自动化测试必须使用 mock"，且接真实
LLM 涉及真实费用和网络依赖，不适合作为可重复的自动化评测。

**后续怎么做**：`docs/EVAL_REPORT.md`（5.4）会写明切换到真实 LLM 跑评测集的方法（只写
方法不实际跑）：改 `.env` 的 `LLM_BASE_URL`/`LLM_API_KEY`/`LLM_MODEL` 指向 DeepSeek，
重跑 `make eval`，同一份 `eval/cases.jsonl` 直接复用。

### 18. Grafana 看板没有做

**现象**：可观测性停留在"每个服务暴露 `/metrics`，Prometheus 格式的指标"这一层，没有部署
Prometheus 服务本身去抓取，也没有 Grafana 看板。

**影响**：要看指标需要手动开 `http://localhost:8011/metrics` 这类地址看原始文本，没有可视化
趋势图。

**为什么没做**：`docs/PHASE3.md` 设计阶段 Jo 因时间原因决定不加 Prometheus 服务容器和
Grafana，题目要求的指标通过各服务自己的 `/metrics` 暴露就够，这是加分项不是硬性要求。

**后续怎么做**：加一个 `prometheus` 服务容器抓取各服务的 `/metrics`，再加一个 `grafana`
服务读 Prometheus 数据源，两者都是标准的 docker-compose 服务定义，不需要改任何业务代码。

### 19. Prompt/模型灰度与回滚没有做

**现象**：LLM 相关配置（`LLM_BASE_URL`/`LLM_MODEL` 等）通过环境变量整体切换，没有按租户/
按比例灰度切流量，也没有"改坏了自动回滚上一版"的机制。

**影响**：换模型/改 prompt 是全量生效的，出问题只能手动改回环境变量重启。

**为什么没做**：题目把这个列在加分项而不是硬性要求，本阶段优先保证核心功能和硬性要求。

**后续怎么做**：需要引入一层路由配置（比如按 `tenant_id` 哈希分流到不同的 `LLM_MODEL`），
以及把 prompt 模板做成可加载可回滚的版本化文件，不是硬编码在代码里。

### 20. OpenTelemetry 链路追踪没有做

**现象**：可观测性靠 `trace_id` 手工在各服务日志里串起来（`app/common/logging.py` 的
`bind_trace_context`），不是标准的分布式追踪协议（OpenTelemetry），没有 Jaeger/Zipkin
这类可视化调用链的工具。

**影响**：排障时要靠 `trace_id` 手动在各服务日志里搜索拼出完整调用链，没有一键看到完整
链路耗时瀑布图。

**为什么没做**：`trace_id` 手工传递已经满足题目"结构化日志带 trace_id"这条硬性要求，接
OpenTelemetry SDK 需要给每个服务加插桩代码，工作量较大，题目没有强制要求。

**后续怎么做**：给 gateway/worker/scheduler 加 OpenTelemetry SDK，把现有的 `trace_id`
映射成 OTel 的 trace context，部署 Jaeger 作为后端。

### 21. 提醒重复规则不含节假日调休

**现象**：`app/common/reminder_rules.py` 的"工作日"重复规则（`ReminderRepeat.workdays`）
只按周一到周五判断，不识别法定节假日、调休上班日（比如调休后的周六算工作日）。

**影响**：法定节假日当天工作日提醒仍然会推送，调休上班的周末不会推送——不完全符合国内
实际工作日历。

**为什么没做**：需要维护一份每年更新的节假日日历数据（国务院年度节假日安排通常年底才公布
下一年的），题目原文只要求"支持重复规则，如每天、每周、工作日"，没有要求对齐法定节假日。

**后续怎么做**：接入一个节假日日历数据源（比如每年手动维护一份 JSON，或者接第三方节假日
API），`reminder_rules.py` 判断"是否工作日"时先查这份日历。

### 22. 模型路由只做了降级到模板，没有做多模型智能路由

**现象**：LLM 不可用时的"降级"只有一种：切换成 worker 自己的关键词兜底规则（
`route_source=rule_fallback`）或固定模板话术，没有"这个问题用便宜模型、那个问题用贵模型"
这类按问题复杂度路由到不同模型的能力。

**影响**：所有 LLM 调用用同一个模型，没有按场景做成本优化。

**为什么没做**：题目把"模型路由"列在加分项（"支持模型路由或降级"，降级已经做了），多模型
智能路由需要额外维护多个模型的接入和路由决策逻辑，本阶段没有做。

**后续怎么做**：在 `app/common/llm_client.py` 加一层路由：简单意图（chitchat/闲聊）用
便宜/快的模型，知识问答/财务这类需要准确性的用更强的模型。

## 阶段五本次发现

### 23. 架构路线图（演示控制台）的几处局限

**现象**：新增的"架构路线图"（`mocks/mock_im/templates/index.html`）有以下已知局限：
- 去程（浏览器→gateway 鉴权→Redis 限流→Redis 去重→RabbitMQ 投递→回 ACK）内部没有分段
  计时数据，图上只标整个去程的 ACK 总耗时，标不出"限流检查花了多久、去重检查花了多久"这类
  更细的分段。
- Redis degraded 状态只在**发消息那一刻**记录一次（`pending[messageId].degradedAtSend`），
  不是持续监控；如果 Redis 在消息发送之后、回复到达之前才变成 degraded，这条消息的路线图
  不会标红（因为记录的是发送时刻的状态）。
- 限流、重复、投递失败、连接被拒这四种情况只在发生的当下播放一次，不进入"点击历史回复
  回放"的列表——因为这几种场景本来就没有对应的 `reply_end`，没有历史记录可以回放。
- "worker 业务流程"框到"回复写入数据库"之间（取消息、数据库唯一约束去重、写库）没有真实
  耗时数据，用固定时长的过渡代替，不代表真实耗时。

**影响**：这是一个演示/讲解工具，不是精确的性能剖析工具，上面几点都不影响功能演示本身要
传达的信息（这条消息走了哪些服务、卡在哪一步、有没有出错），只是耗时精度有限。

**为什么没做**：这几处都要求给对应的后端代码补埋点（`app/gateway/message_handler.py`、
`app/worker/handler.py`），这次需求明确是"纯前端，只改 mocks/mock_im"，不允许改后端接口。

**后续怎么做**：如果要更精确，需要在 `message_handler.py` 的限流/去重/投递三步之间补计时
并通过 `ack` 消息带回给客户端；Redis 状态可以考虑轮询而不是只记一次；这些都需要改动 gateway
的消息协议，超出当前"纯前端"范围。

### 24. 压测第一轮结果作废

**现象**：压测最初一轮用短连接模型的 k6 脚本、且跑的时候 t_a 机构的每日 LLM token 预算
被打满，两个问题叠加导致测不到题目原本要测的路径。

**影响**：第一轮的原始数据保留在 `docs/LOADTEST.md`"第一轮（已作废）"一节供追溯排查过程，
但不能拿那部分数字当最终结论。

**为什么没做**：属于压测准备阶段的设计缺陷（连接模型理解有误）和运行时状态未提前检查
（预算耗尽）叠加导致，发现后已经在第二轮改正。

**后续怎么做**：无需处理，第二轮已经是有效结果，详见
[`docs/LOADTEST.md`](LOADTEST.md#第二轮长连接模型预算已解除--当前有效结果)。

### 25. 敏感操作关键词要求原文连续出现，不支持词序变化

**现象**：`app/worker/graph/classify.py` 的 `SENSITIVE_KEYWORDS =("注销账号", "改密码",
"修改密码", "换绑手机", "解绑手机", "改银行卡", "更换银行卡")` 用的是精确子串匹配
（`if any(k in content for k in SENSITIVE_KEYWORDS)`）。5.4 评测 `sens02`"帮我把银行卡
改一下"实测没有命中——这句话里"银行卡"在前、"改"在后，不包含"改银行卡"/"更换银行卡"这两个
精确子串，落到了普通闲聊分支，没有触发敏感操作的固定拒绝话术。

**影响**：只要用户把动词和宾语的顺序换一下（"银行卡改一下"而不是"改银行卡"），这类涉及
账号安全的敏感操作就会绕过拒绝机制、被当成普通对话处理，是一个真实的安全相关缺口，不是
测试数据的问题——`SENSITIVE_KEYWORDS` 是 `app/worker/graph/classify.py` 里的真实生效
代码，不是 mock。

**为什么没做**：敏感操作关键词表从阶段二写好之后没有再针对词序变化专门测试过，5.4 评测
才第一次实际测出这个边界情况。

**后续怎么做**：参考 `mocks/mock_llm/rules.py` 处理"请个假"命中"请假"的做法——那里把字面
两个连续字的匹配 `"请假" in content` 换成了正则 `请.{0,3}假`，允许中间隔几个字。
`SENSITIVE_KEYWORDS` 可以用同样的思路，把"改银行卡"这类"动词+宾语"的关键词拆成正则
（比如 `改.{0,4}银行卡|银行卡.{0,4}改`，或者更通用地对动词、宾语分别建两个词表分别匹配、
不要求相邻），允许中间隔字和顺序调换。
