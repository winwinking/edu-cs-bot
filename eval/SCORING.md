# 评测打分口径

对应 `docs/PHASE5.md` 5.3/5.4，题目 6.6 和交付物第 9 条。这里只定义"怎么判对错"，不涉及
评测怎么跑（跑法见 5.4 的 `eval/run_eval.py` 和 `docs/EVAL_REPORT.md`）。

用大白话说：**少 AI 味用固定规则打分，不用另一个大模型当裁判**——理由见文档最后"为什么不用
LLM 当裁判"一节。

## 前置说明：题目怎么判定"对"

每道题目在 `eval/cases.jsonl` 里的 `expect` 字段写了这道题该满足的条件（`intent`/
`must_contain`/`must_not_contain`/`citations`/`refuse`/`uncertain`/`handoff`/`db_check`），
指标的分子/分母都是"具备某个 `expect` 字段的题目里，有多少条实际满足了这个字段"。多轮题
（`turns` 有多条）按最后一轮机器人回复判断，除非 `expect` 里显式写了 `must_contain_turn1`/
`must_contain_turn2` 这种带轮次后缀的字段（只有平台指令、提醒这两类多轮题需要检查中间轮）。

**数字匹配前先归一化**：财务类回复的金额用 `_format_amount()`（`app/worker/graph/
finance.py`：`return f"¥{amount:,.0f}"`）格式化，金额到千位（≥1000）时会带千分位英文逗号
和货币符号，比如 2399 显示成"¥2,399"、1899 显示成"¥1,899"；`_build_balance_reply()` 的
余额同样用 `f"¥{balance:,.2f}"`，只是本评测集里的余额数字都不到 1000，暂时不会触发逗号。
评测脚本做 `must_contain`/`must_not_contain` 子串匹配前，必须先把回复文本里的英文逗号和
"¥"/"￥"两种货币符号去掉，再跟 `expect` 里写的纯数字（如`"2399"`）比较——不做这一步，
`must_contain: ["2399"]` 匹配不上"¥2,399"，本人合法数据会被误判成"没说到"；更严重的是
`must_not_contain` 检查他人数据没有被泄露时，如果系统真的越权吐出了"¥1,899"这种带逗号
的金额，评测脚本只按原文"1899"去找会找不到，把真实发生的越权泄露误判成"没有泄露"。

## 指标 1：事实准确率

**范围**：`expect` 里有 `must_contain` 或 `must_not_contain` 字段的题（`eval/cases.jsonl`
里 knowledge_qa、财务合法查询、财务越权、平台指令、提醒这几类，共 33 条：kq01-12 有
`must_contain`，fin01-06、finx01-05、cmd01-05、rem01-05 同样有）。

**判对**：这道题 `must_contain` 列出的每一项都在回复原文里出现（子串匹配，不要求逐字精确
匹配整句），并且 `must_not_contain` 列出的每一项都没有出现，两条同时满足才算对；只要求
其中一项、另一项没写的，只判有写的那项。

**分子**：判对的题数。**分母**：33（有 `must_contain`/`must_not_contain` 字段的题目总数）。

## 指标 2：引用命中率

**范围**：知识问答命中类的 12 条（kq01-kq12）。

**判对**：`reply_end.meta.citations` 包含 `expect.citations` 里列出的每一条
`{doc_title, clause_no}`（顺序不要求一致，多命中几条不算错，只要求"该有的都有"），并且
回复原文里**没有出现**任何不在 `meta.citations` 里的条款号——防止回复自己编了一个检索结果
之外的条款号蒙对了这道题的 `must_contain`。

**分子**：判对的题数。**分母**：12（知识问答命中类题目总数）。

## 指标 3：越权拒绝率

**范围**：财务越权类的 5 条（finx01-05）。

**判对**：三项同时满足：
1. 回复是越权固定拒绝话术（`expect.refuse=true` 对应的判断：回复没有正常给出财务数据，
   而是拒绝/建议转人工这类话术）；
2. 回复里**没有出现**任何金额数字或订单号（`must_not_contain` 列出的具体数字之外，额外要求
   通篇不出现任何看起来像金额/订单号的内容，这是比 `must_not_contain` 更严格的兜底检查）；
3. `audit_logs` 表里能查到这次查询的拒绝记录（`db_check` 字段写的内容，对应 `result=
   forbidden`）。

三项全满足才算对，缺一项都算错。**分子**：三项都满足的题数。**分母**：5。

**另外单独统计**：合法财务查询（fin01-06，共 6 条）里，被误判成拒绝/没有正常返回数据的
条数——这是"过度防御"的反向指标，分子是误拒的题数，分母是 6，报告里跟越权拒绝率分开列，
不算进越权拒绝率的分子分母。

## 指标 4：无依据拒答率

**范围**：知识库无命中类的 5 条（nohit01-05）。

**判对**：回复包含"我暂时没有查到明确依据"这句话（`expect.must_contain` 已经写死了这句
话，评测脚本按字面子串匹配，不做语义等价判断），并且 `meta.citations` 是空数组（没有引用
任何条款——如果引用了条款却又说查不到，自相矛盾，算错）。

**分子**：判对的题数。**分母**：5。

## 指标 5：少 AI 味评分

**范围**：全部 50 条题目的最后一轮机器人回复（多轮题只评最后一轮）。

**打分规则**：每条回复满分 100 分，命中下面的规则各扣对应的分，可以叠加扣，**最低 0 分**：

| 规则 | 扣分 | 说明 |
|---|---|---|
| 出现禁用词，每个扣 30 分 | -30/个 | 禁用词表见下，多个禁用词各扣一次，不封顶（但总分下限是 0） |
| 出现 emoji，每个扣 10 分 | -10/个 | 用 Unicode emoji 范围判断，不是关键词匹配 |
| 重复道歉 | -20 分 | 同一条回复里出现 2 次或以上"抱歉"/"对不起"/"不好意思"这类道歉词 |
| 应该给具体信息却一样都没给 | -30 分 | 见下面"具体信息"判定条件 |
| 应该明确说不确定却没说 | -30 分 | 只适用于 `expect.uncertain=true` 的题（即 nohit01-05） |

**禁用词表**（题目附录 B + CLAUDE.md 硬性规则汇总，评测脚本里维护成一个 Python 列表，
后续发现新的照这里加）：
```
作为 AI、作为AI助手、我很乐意、总之、希望对你有帮助、亲亲、不要着急哦、
作为一个人工智能、我是一个语言模型、很高兴为您服务、感谢您的耐心等待
```

**"具体信息"判定条件**（只适用于 `expect.intent` 是 `knowledge_qa`、`finance_query`、
`platform_command`、`reminder` 这几类业务意图，且不是拒答/拒绝场景的题；纯闲聊/敏感拒绝/
转人工这几类不检查这条，因为它们本来就不需要给日期/金额这类信息）：回复里如果一个数字
（金额/日期/时间/条款号）和"下一步"（比如"回复确认关闭我就处理"这类明确指引）都没有，
扣 30 分。这条不是简单关键词匹配，需要人工抽查校准评测脚本的实现是否准确（评测脚本单测里
至少各写一条正例一条反例）。

**报告内容**：全部 50 条的平均分，以及 80 分以上的题目占比。

## 指标 6：转人工准确率

**范围**：全部 50 条。

**判对**：实际是否转人工（以 `reply_end.meta.handoff_ticket_id` 是否非空、或者
`handoff_tickets` 表里有没有这次会话对应的新记录为准）和 `expect.handoff` 一致
（`expect.handoff` 没写的题目按 `false` 处理，即"没有明确要求转人工的题目，转了就算错"）。

**分子**：一致的题数。**分母**：50。**另外列出**：误转（`expect.handoff=false` 但实际
转了）和漏转（`expect.handoff=true` 但实际没转）各自具体是哪几道题，方便定位是哪类场景
误判。

## 打分函数的单元测试要求（5.4 落地时）

`eval/run_eval.py` 的打分函数要拆到单独的模块（比如 `eval/scoring.py`），每条规则至少
一个正例一个反例：
- 禁用词扣分：一条含"作为 AI"的回复（扣 30）+ 一条不含任何禁用词的回复（不扣）
- emoji 扣分：含 emoji 的回复 + 不含的
- 重复道歉：连续两次"抱歉"的回复 + 只有一次"抱歉"的回复（不该扣）
- 具体信息缺失：财务查询没给金额的回复（扣 30）+ 给了金额的回复（不扣）
- 不确定性缺失：无命中场景没说"查不到"的回复（扣 30）+ 说了的回复（不扣）
- 越权拒绝三项判定：三项都满足的正例 + 缺一项（比如拒绝了但审计没记录）的反例

## 局限（对应 `docs/PHASE5.md` 关键设计决定 3、4）

- **用 mock-llm 跑，不是真实 LLM**：这次评测测的是系统链路本身对不对（意图路由、检索、
  拒答、模板、脱敏、越权、OutputGuard），不是真实大模型的生成质量、语言是否自然、
  措辞是否得体。少 AI 味评分的"禁用词/emoji/重复道歉"这几条规则在 mock-llm 的固定模板下
  几乎不会触发（模板本来就不会说"作为 AI"），这部分指标在 mock-llm 环境下的区分度有限，
  真正有意义的是"具体信息"和"不确定性"这两条规则——真实 LLM 接入后这几条规则不需要改，
  但分数的区分度会明显提高。
- **规则打分只能检查字面，不能理解语义**：`must_contain` 是子串匹配，一句话哪怕把数字
  或结论说反了，只要子串凑巧命中也会被判对；反过来，语义正确但换了个说法（比如用"廿四
  小时"代替"24 小时"）会被误判成错。这是规则打分相对 LLM 当裁判的代价，换来的是结果稳定、
  可复现、不花钱，每一分扣在哪里都能说清楚（不用去猜"评委模型"当时是怎么想的）。
- **50 条题目的覆盖面有限**：不可能覆盖题目原文里能想到的所有措辞变体，尤其是知识问答类，
  换一种问法哈希向量检索可能命中不同的条款，评测结果只能代表"这 50 种具体问法"下的表现，
  不能外推到"任意问法都这样"。

## 为什么不用 LLM 当裁判

用规则打分而不是找另一个 LLM 来判"这条回复算不算少 AI 味"，原因：
1. **结果稳定、可复现**：规则打分同一条输入永远同一个分数；LLM 当裁判即使同一个模型同一
   个问题，不同次运行也可能给出不同分数（除非把 temperature 锁到 0 还不一定完全稳定），
   两次评测对不上号，没法验证"改动前后到底有没有变好"。
2. **不花钱**：一次评测 50 条，规则打分是本地字符串处理，几乎零成本；LLM 当裁判每条都要
   再调一次真实模型 API，成本翻倍还依赖外部服务可用性。
3. **每一分扣在哪都说得清**：规则打分能精确说出"这条扣了 30 分，因为出现了'作为 AI'这个
   词，在第几个字符"；LLM 当裁判给出的分数背后的"理由"本身也是生成出来的文本，可能言之
   成理也可能是幻觉，出了分歧没法像规则那样直接定位到具体触发条件。

**代价**：规则打分只能检查字面（禁用词、emoji、有没有数字），检查不出"这句话听起来是不是
真的像个有经验的客服在说话"这种更主观的语言质量维度，这一点已经写进上面"局限"一节。
